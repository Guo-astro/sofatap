# Focused text field detection and live editing

Sofatap can offer the phone keyboard when the desktop reports a focused, writable text field. This is an accessibility hint, not proof that an application will accept input. Manual keyboard and dictation controls remain necessary for applications that do not expose useful accessibility metadata. The receiver must suppress this hint whenever its desktop is locked or unavailable.

The native probes return `unknown`, `other`, `editable` or `protected`, with an ephemeral random identity for detecting a change of target inside the receiver. Only the state and a connection-local revision cross the network; the identity stays local. These background probe queries do not request field values, selected text, passwords, labels, window titles or screenshots. The separate explicit live-editing session described below does read the current supported field's text and selection. Platform accessibility libraries may populate internal caches with incidental names/descriptions or event metadata; Sofatap does not inspect or log those fields, or include them in the helper output or network messages. There is no input injection, accessibility action or clipboard access in these probes. The identity carries no native element ID, process ID or persistent identifier.

## Windows

The receiver asks UI Automation for the focused element. It reads keyboard-focus, enabled and password flags, then Value-pattern read-only metadata. A Text-pattern `IsReadOnly` attribute provides a fallback for editable documents, including browser controls that expose that pattern. Read-only, missing and mixed metadata do not cause a keyboard to open. Password fields are reported as `protected` before text-pattern queries.

All COM calls run on one dedicated MTA background thread. `Read()` returns cached metadata immediately. If an application's automation provider stalls, the cache expires after 1.5 seconds and returns `unknown`; repeated requests do not create additional threads. The stalled provider cannot block receiver shutdown, although its background thread remains until the provider returns or the process exits. Elevated or custom-rendered applications may not expose accessible controls to an ordinary receiver.

## macOS

The receiver uses the existing Accessibility grant. It does not request permission or open System Settings. It checks the focused element's role, secure-text subrole, enabled flag and whether its value attribute is writable; it never reads that value. Recognized text fields, text areas and editable combo boxes qualify. Secure fields report `protected`.

AX calls have a 150 ms messaging timeout per call, run on the same bounded cache worker and verify that the focused element did not change during sampling. Applications whose editable controls do not expose writable-value metadata fall back to manual keyboard access. Live UI acceptance must follow this repository's Yomado virtual-display and input-isolation requirements.

## Linux

An optional Python/Gio helper subscribes directly to AT-SPI focus events on the accessibility D-Bus. It needs `python3-gi` with Gio 2.0, a working accessibility bus (normally `at-spi2-core` on Debian/Ubuntu), and applications that publish AT-SPI state. The Atspi typelib is not required by the helper. It does not modify accessibility settings, load libatspi's object cache, crawl application widgets or create application P2P connections. Only focused-object `GetState` and `GetRole` are requested; field values, names, descriptions and `Cache.GetItems` are never requested. Incidental focus-event payloads are ignored.

The two metadata calls run asynchronously with 200 ms deadlines, only one pair in flight. Changing focus cancels the previous pair; late replies cannot overwrite a new target or a newer request. Metadata expires after one second in the helper, independently of the host's cache expiry. The initial state is `unknown` until the next focus event. Focused enabled editable controls qualify; password-text roles report `protected`; stale, missing or defunct targets report `unknown`.

X11 or Wayland session type alone is not sufficient. RemoteDesktop portal permission is unrelated to accessibility support. When the helper/dependency is missing, its bus fails or a metadata read times out, automatic keyboard detection falls back to `unknown`; normal manual input remains independent. The helper is owned by the receiver and has no network listener or input-event capability.

## Live editing sessions and data handling

When the phone editor opens, a compatible receiver attempts live editing by default. `textBegin` reads only the currently focused supported field and returns its complete plain text plus UTF-16 selection. This is a separate operation from the background focus hint, and it also occurs when that hint opens the phone editor automatically. Backspace, selection changes, Select All → Delete, confirmed IME text and partial speech corrections then synchronize through `textSync`. There is no Send button in an active live session.

Windows live editing supports normal native Unicode Edit/RichEdit controls in the receiver's unlocked desktop/session. Password, read-only, elevated, foreign-session, browser and other custom controls are rejected. Native control messages replace only the changed text span, preserve surrounding text/formatting, normalize native newlines to LF for the phone, and read back both text and selection. Mac live editing requires a normal enabled AX text field, text area or combo box with readable text and writable `AXSelectedText` and `AXSelectedTextRange`; secure or unsupported fields are rejected. It replaces the selected difference through `AXSelectedText`, never rewrites the whole `AXValue`, and verifies exact readback. macOS live input has not yet had physical-device acceptance. Linux has no precise live backend yet. Unsupported targets and older receivers retain the review-and-send composer.

A session has one target and a revisioned acknowledged snapshot. Focus, native text or selection conflicts end that session; interrupted or uncertain edits pause the phone rather than triggering retries or rollback. Reopen editing explicitly after inspecting the computer. The native APIs do not offer an atomic compare-and-swap across external user edits: bounded before/after verification detects conflicts, but an uncertain result still requires inspection. An ACK confirms field readback, not application save or form submission.

The complete current field text and selection travel directly over the existing pinned TLS connection to the paired phone. Imported live text stays in phone memory and is not stored in its saved fallback-draft preferences. The receiver retains bounded text-bearing ACKs in memory for duplicate suppression for the lifetime of the controlling connection. Text is not logged or sent to a hosted service. Native target identities stay inside the receiver. This differs from the fallback draft, which remains locally saved on the phone until cleared. Neither mode reads or replaces the clipboard.

## Verification boundaries

Pure tests cover metadata classification, protected/read-only precedence, malformed helper messages, stale-cache expiry and a deliberately stalled provider. They never query or control the user's desktop. `desktop/linux/check_text_focus_integration.py` creates its own authenticated Xvfb display and private D-Bus session, then verifies the real AT-SPI worker against owned blank GTK entry, read-only, password and button widgets. It refuses to use an existing desktop. Native provider compilation does not establish end-to-end focus detection in every application; actual Windows/macOS/browser and Wayland application coverage still require isolated acceptance testing.
