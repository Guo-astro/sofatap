# Free TV control: implementation and qualification plan

[简体中文](tv-implementation-plan.zh-CN.md)

Research date: **2026-10-13, Asia/Tokyo**. Status: **engineering proposal and source inspection**, not a TV compatibility announcement. No television, phone, Bluetooth device or desktop was operated for this research. Any implementation developed alongside this document has its own build and acceptance evidence.

The product sequence is **free manual TV control → paid Windows/macOS/Linux voice automation → paid TV voice automation**. Manual gestures, typing and speech-to-text remain basic input features. The first TV release must work without an AI model, Codex, subscription or cloud account. See [the roadmap](../ROADMAP.md) and [the preceding TV research](direct-tv-control.md).

## Current priority: Android/Google TV receiver feasibility

Build and qualify a **shared native Android TV receiver** first. This supersedes the earlier LG-first recommendation: the LG protocol preview remains useful, but does not determine the next target platform. Begin with an installable capability probe, then pair it with the existing iPhone touch surface only after the required input routes are demonstrated. No Android receiver APK or hardware qualification is claimed by this document.

Use one Android codebase with capability detection and model/firmware-specific qualification, rather than separate brand apps. Native TV UI must be operable with the existing remote, show a local pairing QR code without a browser, and explain accessibility and optional input-method setup. A QR code establishes a pairing opportunity, not input permission. Bind the one-time, expiring pairing secret to the receiver's cryptographic identity, authenticate subsequent traffic, provide revocation and reject unauthenticated commands. Keep QR contents, input text and keys out of logs.

The first probe must distinguish native mouse input, overlay-cursor node activation, direction navigation and unsupported operations. Measure clicks and scrolling in launcher, Settings and representative third-party apps; test touch/faketouch availability and accessible-node coverage before committing to gesture injection. A moving overlay alone does not complete the pointer milestone. Add an optional IME only with explicit user enablement and verify editing through the focused `InputConnection`.

Produce an **APK for direct installation/testing** and an **AAB for eventual Google Play TV submission**, from the same app project. Declare the TV launcher and touchscreen-not-required features, support remote-only onboarding, and check current TV quality, architecture and page-size requirements before distribution. Sources: [native TV app structure](https://developer.android.com/training/tv/get-started/create), [Google Play TV distribution](https://developer.android.com/training/tv/publishing/distribute). Packaging does not grant system input permissions or guarantee store acceptance.

Remote v2 remains a separate **directional touch remote** route when the TV already has Android TV Remote Service; that route may need no Sofatap receiver. It is not a substitute for the pointer feasibility milestone. LG webOS retains its native iOS adapter and TV approval flow, without requiring a Sofatap TV app on compatible firmware. Automatic LG SSDP discovery and hardware qualification remain later work.

## LG webOS protocol and trust

The implementation reference is LG's ConnectSDK Android Core at [`2f7ebbc7eb909321ff41b2c6bcdf6b0881427579`](https://github.com/ConnectSDK/Connect-SDK-Android-Core/tree/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579). Port the narrow protocol boundary into Swift rather than embedding its entire Android framework. Retain Apache-2.0 notices for copied/adapted source and review any additional dependencies. These are second-screen SSAP implementation details; the public [Luna API documentation](https://webostv.developer.lge.com/develop/references/luna-service-introduction) is not a guarantee that every TV-local Luna method is remotely available over SSAP.

### Discovery and identity

ConnectSDK discovers `urn:lge-com:service:webos-second-screen:1` through SSDP. Its SSDP client sends M-SEARCH to IPv4 multicast `239.255.255.250:1900`. Parse bounded responses and the advertised device description; retain the TV's identifier, model and last address. Treat the friendly name, description URL and network address as untrusted discovery data, not authenticated identity. Reject unexpected schemes, external redirects and excessively large descriptions. Re-discovery after DHCP changes must not silently replace the paired certificate or key. Sources: [service filter](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/WebOSTVService.java#L228), [SSDP transport](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/discovery/provider/ssdp/SSDPClient.java#L37).

On iOS, local access requires a meaningful `NSLocalNetworkUsageDescription`; raw SSDP multicast additionally requires `com.apple.developer.networking.multicast` in the signed entitlement/profile. Declaring Bonjour service types alone does not grant SSDP access. A normal declared Bonjour browse and custom multicast have different requirements. Test permission denial, later approval and guest-network isolation. Do not hide entitlement failure behind a subnet scan. Source: [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

### Registration and credential lifecycle

The inspected client connects to **`wss://<TV>:3001`** and sends a JSON `register` message with an ID, a manifest and, on reconnect, the saved `client-key`. It understands both TV prompt and PIN pairing; PIN uses `ssap://pairing/setPin`. Only the final `registered` response establishes registration and provides the returned key. A socket opening or a pairing prompt is not success. Sources: [WSS endpoint](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVServiceSocketClient.java#L87), [registration](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVServiceSocketClient.java#L591).

Registration is a dedicated handshake phase: if a response ID exists, require it to match; allow a missing ID only for the expected handshake message in the current connection generation. ConnectSDK handles `registered` independently and removes its pending request only when an ID exists. The maintained `aiowebostv` client also reads registration separately from its normal ID-correlated request loop. After registration, keep strict request-ID correlation, including the pointer-socket request. For its success payload, reject an explicit false `returnValue` or error response, but do not require a field solely because another API uses it: ConnectSDK's pointer handler requires `socketPath`, without checking `returnValue`. Treat this as an interoperability rule to test, not proof of every TV's response shape. Sources: [registered handler](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVServiceSocketClient.java#L349), [independent client handshake](https://github.com/home-assistant-libs/aiowebostv/blob/ba7acf42ae55635ff4b527e80abda32d305590e1/aiowebostv/webos_client.py#L218), [pointer response](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/WebOSTVService.java#L1496).

Proposed session states: `disconnected → connecting → awaitingTVApproval → registered → pointerReady`, with explicit `rejected`, `expired`, `trustChanged` and `unavailable` exits. The TV must identify the controller as Sofatap. Store the client key and certificate pin in Keychain, bound to the selected TV record and permission-manifest version. Keep them out of analytics, logs, screenshots, Git and backup fixtures. “Forget TV” removes local authority; explain separately how to revoke the controller on the TV where available.

The source's basic manifest contains `manifestVersion: 1` and a permissions array. Candidate initial permissions are `CONTROL_MOUSE_AND_KEYBOARD` for pointer control and `CONTROL_INPUT_TEXT` for typing. Whether a given firmware additionally requires `CONTROL_INPUT_JOYSTICK` must be tested; this is **not yet a verified minimum manifest**. Add `CONTROL_AUDIO` or playback permissions only when those controls ship. Do not request installed/running-app lists, channel history, updates or unrelated permissions for the pointer milestone. Permission changes can require re-pairing. Do not copy another application's signed manifest, vendor identity or signature. Sources: [manifest construction](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVServiceSocketClient.java#L222), [permission names](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVDeviceService.java#L134), [permission-change behavior](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/WebOSTVService.java#L2517).

### TLS must cover both sockets

Local televisions can present certificates that ordinary public-CA/hostname validation does not accept. Implement a narrowly scoped first-pairing trust flow, then pin the accepted TV certificate for later sessions. Require explicit re-pairing when identity changes. First-use local trust is not a vendor-authenticated or MITM-proof channel; the TV confirmation and persistent pin reduce different risks. Never send a saved client key to an unrecognized certificate. Do not silently fall back to plaintext `ws://` or disable trust checks globally.

Use ConnectSDK as protocol evidence, not as a security template: its trust manager accepts a certificate when no expected certificate exists; its configuration loader leaves certificate restoration as a TODO; its pointer client creates a fresh trust manager without setting an expected certificate. Its certificate self-signature check also does not establish vendor identity. Sofatap must close these gaps with persistence and target-bound validation. Sources: [trust manager](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVTrustManager.java#L31), [configuration loading](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/config/WebOSTVServiceConfig.java#L64), [pointer TLS](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVMouseSocketConnection.java#L99).

After registration, request `ssap://com.webos.service.networkinput/getPointerInputSocket`. The returned `socketPath` is an ephemeral capability: validate scheme, selected-TV host/address and permitted port before connecting, authenticate its certificate, and never log the complete URL. Require the same pin unless a distinct authenticated binding is actually verified. Obtain a fresh pointer URL after reconnection; do not persist or replay old URLs. Source: [pointer acquisition](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/WebOSTVService.java#L1487).

### Gestures and reconnect behavior

The pointer channel uses newline-delimited text ending in a blank line. The source implements `type:move` with relative `dx`, `dy` and `down:0`; `type:click`; and `type:scroll` with `dx/dy`. It also implements named Home/Back/direction buttons. A lower-level move variant sends `down:1`, but that is not independent validation of complete drag/drop. No separate right-button operation appears in this implementation. Source: [pointer messages](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVMouseSocketConnection.java#L135).

Map one-finger motion to relative movement, a tap to click and two-finger movement to scrolling. Disable unsupported right-click/drag rather than silently mapping desktop gestures to unrelated TV actions. Coalesce motion into bounded updates with residual-delta accumulation; preserve click ordering and flush relevant motion before a click. Clear pending deltas on device switch, socket loss, suspension and reconnection. Never replay an old click after reconnecting.

Treat SSAP responses and pointer writes differently: an SSAP success confirms a protocol response; a successful pointer write does not prove the target app changed. Rebuild subscriptions and pointer state after re-registration. Use bounded reconnect backoff and session generations so late responses cannot affect a new TV/session. App backgrounding stops new manual commands. Reconnection restores readiness, not a backlog of input.

LG documents pointer and 5-way focus as separate modes; arrow keys can hide the pointer. Scroll handling and active overlays affect which UI receives input. Verify pointer recovery after D-pad use and after Home/Settings overlays, rather than assuming every app acts like a desktop browser. Source: [LG Magic Remote behavior](https://webostv.developer.lge.com/develop/guides/magic-remote).

### Text, dictation and editing

Subscribe to `ssap://com.webos.service.ime/registerRemoteKeyboard`. ConnectSDK reads `currentWidget.focus`, `contentType`, `hiddenText` and `focusChanged`, then sends `insertText`, `deleteCharacters` with `count`, and `sendEnterKey`. Its insertion uses `replace: 0`; the source does not establish arbitrary range replacement, selection synchronization or full editor readback. Source: [keyboard implementation](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVKeyboardInput.java#L44).

Auto-open the phone keyboard only for a qualified active text focus; invalidate editing state on focus changes. Preserve the existing desktop realtime editor contract, but give TV text a separate capability description. Initially send committed IME text and finalized dictation segments automatically, without a Send button. Keep provisional recognition/composition local unless replacement semantics have been verified. Full synchronized backspace, select-all, selection and speech corrections are a later TV acceptance gate; blind deletion/reinsertion can corrupt pre-existing or externally edited text. A disconnected or uncertain text operation must not be retried automatically. Test Chinese/Japanese composition, emoji deletion units and app-specific search fields independently. Treat protected fields as protected and never retain their contents.

## Android/Google TV: two distinct routes

### Remote v2 for ordinary consumer setup

The maintained [`androidtvremote2` implementation at `e664a8e1f14ee458b14c646bfb3ea46f10367051`](https://github.com/tronikos/androidtvremote2/tree/e664a8e1f14ee458b14c646bfb3ea46f10367051) uses the preinstalled Android TV Remote Service, without ADB or developer mode. Source ports are 6467 for pairing and 6466 for control. Pairing retains a client certificate/private key; it is not the LG `client-key` protocol. A new TV app is unnecessary when the required service exists. This is interoperable implementation evidence, not a Google-supported third-party SDK contract. Sources: [library scope](https://github.com/tronikos/androidtvremote2/blob/e664a8e1f14ee458b14c646bfb3ea46f10367051/README.md), [transport and pairing](https://github.com/tronikos/androidtvremote2/blob/e664a8e1f14ee458b14c646bfb3ea46f10367051/src/androidtvremote2/androidtv_remote.py#L53).

Its current schema exposes key injection, IME, voice, power/volume and app links, **not relative pointer or wheel messages**. `SHORT`, `START_LONG` and `END_LONG` describe key actions. Google's use of the word “touchpad” is not evidence for a freely positioned mouse. Implement swipe-to-direction and tap-to-center explicitly as directional mode; test key release on cancellation. Do not copy the reference's `CERT_NONE` TLS policy into production. Sources: [message schema](https://github.com/tronikos/androidtvremote2/blob/e664a8e1f14ee458b14c646bfb3ea46f10367051/src/androidtvremote2/remotemessage.proto#L846), [Google Remote Service](https://play.google.com/store/apps/details?id=com.google.android.tv.remote.service).

### A TV companion does not automatically solve true mouse input

An ordinary Android application cannot obtain the signature-only `INJECT_EVENTS` permission for arbitrary system input. Accessibility services can operate accessible nodes and global actions after the user explicitly enables them, but gesture injection is different from mouse injection. AOSP at `1cdfff555f4a21f71ccc978290e2e212e2f8b168` requires a touch/faketouch device for `dispatchGesture`; its motion injector produces touchscreen events with button state zero. A rendered overlay cursor plus these actions is an experimental accessibility controller, not verified universal mouse hover, right-click, wheel or drag. Sources: [input permission](https://android.googlesource.com/platform/frameworks/base/+/1cdfff555f4a21f71ccc978290e2e212e2f8b168/core/res/AndroidManifest.xml#5365), [gesture device gate](https://android.googlesource.com/platform/frameworks/base/+/1cdfff555f4a21f71ccc978290e2e212e2f8b168/services/accessibility/java/com/android/server/accessibility/AccessibilityServiceConnection.java#544), [injected event type](https://android.googlesource.com/platform/frameworks/base/+/1cdfff555f4a21f71ccc978290e2e212e2f8b168/services/accessibility/java/com/android/server/accessibility/MotionEventInjector.java#59), [service setup](https://developer.android.com/guide/topics/ui/accessibility/service).

A custom Android `InputMethodService` can commit/composite text and delete through the focused editor's `InputConnection`; it requires installation, enabling and selection as an input method. Custom canvases, games and editors that do not expose the expected connection remain limitations. Accessibility node text operations are likewise app-dependent. Neither route grants general raw mouse injection. The initial TV-side setup still needs an existing remote or working direction-control path. Sources: [IME design](https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method), [TV distribution](https://developer.android.com/training/tv/publishing/distribute).

The native Android receiver experiment is now the next feature milestone. Require normal installation/permission onboarding; developer ADB, root, shell injection or OEM signing cannot be the ordinary-consumer default. If the tested accessible-node route cannot deliver the required pointer experience, report that result before promising general support. OEM/system integration or a separate hardware input bridge would be a distinct product dependency to evaluate, not an implied software-only capability.

## Why direct iPhone Bluetooth HID is not the first route

No verified, supported public-iOS implementation was established here that makes Sofatap a standard Bluetooth mouse/keyboard for arbitrary TVs. CoreBluetooth peripheral/GATT support alone is insufficient evidence for publishing a usable HID device profile. Apple DTS identifies HID as a system-handled service with restrictions; that discussion directly establishes filtering in a client scenario, not a complete proof that every possible peripheral route is prohibited. Therefore retain **“unverified and not a release dependency”**, rather than an absolute impossibility claim. Source: [Apple DTS HID discussion](https://developer.apple.com/forums/thread/845352).

Use local Wi-Fi adapters for this release. A future dedicated BLE/USB HID bridge would add hardware, pairing, power and compatibility requirements and needs separate authorization and research.

## Shared architecture and release gates

Add a device-adapter boundary behind the existing phone control surface. Model capabilities separately: `relativePointer`, `click`, `scroll`, `heldDrag`, `secondaryClick`, `directionKeys`, `textAppend`, `textDelete`, `textFocus`, `textSelection` and `textReplacement`. Give capability state a protocol basis plus a qualified model/firmware override; do not infer support from a product name. Keep desktop text revisions/acknowledgments separate from TV IME and fire-and-forget pointer semantics. No adapter should expose arbitrary SSAP URIs supplied by UI or future model output.

Use one active target/session and serialize mutations. Selection of another device cancels the old input owner before opening the new one. Store only pairing state required for reconnect; keep manual-control telemetry content-free. Test pairing rejection, wrong device/address, changed certificates, malformed responses, oversized messages, stale subscriptions and expired pointer URLs with local protocol fixtures before hardware tests.

| Stage | Evidence required before proceeding |
| --- | --- |
| 1. Android receiver capability probe | Build an installable native TV APK. On named hardware record OS/firmware, touch/faketouch features, accessibility enablement, node click/scroll coverage and optional IME behavior. Test outside the receiver's own UI. Explicitly decide whether the pointer experience is feasible before advertising it. |
| 2. Native phone-to-TV loop | Native QR pairing with authenticated transport, permission-denial recovery, first pairing/reuse/revocation, movement, actual target activation, supported scrolling and Back/Home. Test bounded queues, stale sessions and wrong-target rejection. Keep desktop control inactive while TV owns input. |
| 3. Input robustness | Repeated mixed gestures; Unicode/IME/dictation; focus switches; no dropped/duplicate text or wrong-target input; phone backgrounding, Wi-Fi loss, DHCP change and TV reboot. Record unsupported editor operations explicitly. |
| 4. Consumer readiness | Native discovery and fallback, required iOS network permissions/entitlements for the chosen discovery method, localized remote-only onboarding, credential removal and signed APK/AAB distribution checks. Test at least two named firmware/model families before broadening the list. |
| Separate adapters | Remote v2: qualify service versions, pairing, key holds/releases, navigation, text and reconnect. LG webOS: qualify the existing pointer preview on named hardware. Neither route substitutes for Android receiver acceptance. |

Set and measure a responsiveness target during the spike; do not claim latency from source. Retain short device-visible evidence for every passed capability. A changing phone animation, an SSAP response or a remote focus rectangle does not prove a real TV pointer moved.

Wake is an independent feature: network standby/settings, firmware and network interface determine whether a sleeping TV is reachable. The inspected ConnectSDK `powerOff` exists while `powerOn` reports unsupported. Do not promise wake from unplugged/deep-off states or treat Wake-on-LAN as already implemented. Qualify standby behavior separately and keep the first loop powered-on. Source: [power implementation](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/2f7ebbc7eb909321ff41b2c6bcdf6b0881427579/src/com/connectsdk/service/webos/WebOSTVDeviceService.java#L670).

Any shared-Mac fixture windows must stay in Yomado's virtual display with verified input isolation, unchanged physical-display arrangement and restored placement afterward. Moving a window alone is insufficient. TV acceptance should use the authorized TV and test phone without commandeering the user's desktop session.

## Later paid features

After free TV control, execute the [paid desktop automation plan](natural-language-pro.md) on Windows/macOS/Linux. Only afterward extend paid voice tasks to validated TV commands and observations. Neither pi-durable nor Cua supplies an Android/webOS execution backend merely by being integrated. A remote-input protocol also does not establish screenshot access, a UI tree or visibility into protected video.

For any future Android Accessibility-based agent, Google Play explicitly distinguishes deterministic human-defined automation from autonomous planning/execution through AccessibilityService. An initial user goal is not a stated exemption; ordinary Sofatap is not a disability-tool exception. The restriction concerns that API, not every natural-language command sent through a legitimate TV protocol. Evaluate the actual paid-TV implementation before promising cross-app autonomy. Source: [Google Play AccessibilityService policy](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en).

The immediate deliverable is the free Android/Google TV receiver capability probe, followed by a locally paired manual-control loop if its input capabilities pass. The LG preview remains separate, and real hardware acceptance is required for every advertised TV capability.
